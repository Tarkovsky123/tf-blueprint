# TF 청사진 (tf-blueprint)

**혼자서도 컨설팅 팀이나 증권사 리서치 팀처럼 일하게 해 주는 틀.** 새 프로젝트를 시작하면 하나의 TF(태스크포스)를 꾸려 준다. 사용자는 **대표**로서 방향을 정하고 승인한다. AI(Claude Code나 Codex)는 **수석 비서이자 노련한 파트너**로서 일정과 기록을 챙기고, 답을 먼저 제안하고, 품질 기준에 못 미치면 멈춰 세운다.

```
python tf.py new "거래처 유지 전략" --mode consulting --deadline 2026-11-13 --path ../my-tf
```

이 한 줄로 헌장 양식, 단계별 일정, 관문, 첫 할 일 19개, AI 운영 지침(`AGENTS.md`·`CLAUDE.md`)이 든 폴더가 생긴다. 그 폴더를 Claude Code나 Codex로 열고 "브리핑해 줘"라고 하면 된다.

## 무엇을 하나

| | 하는 일 |
|---|---|
| **틀 잡기** | 팀 방식(컨설팅 / 증권사 리서치)을 고르면 착수 → 3단계 → 전달까지 5단계와 관문 5개(G0~G4)를 마감에 맞춰 배치하고, 단계마다 할 일을 미리 깔아 둔다. AI는 한 번에 한 질문씩 착수 인터뷰를 해서 헌장(핵심 질문·성공 기준·범위·기준 시점·레드팀 관점·자료)을 채운다 |
| **진행** | 세션마다 수석 비서 브리핑: 지난 세션 인계, 마감 D-day, 대표 결정 대기(며칠째), 늦어진 일, 다가오는 일정·촉매, 대표에게 요청한 자료(며칠째), 가설별 진척, 열린 리스크, 일정 경고, "지금 할 일 3개". 할 일은 검증할 가설에 묶이고, 하지 않기로 한 일은 이유와 함께 취소하며, 마감이 바뀌면 남은 단계를 다시 배분한다 |
| **정확도** | 모든 사실에 출처 번호 `[S3]`(출처마다 쪽·표 위치와 확인일), 가정은 `[가정]`, 계산·추정은 근거 파일까지 `[계산: work/model.py]`. `tf.py check`가 근거 없는 숫자, 없는 출처, 미확인 출처, 위치 없는 출처, 파일 없는 계산, 덜 쓴 표시, 결론이 먼저 오지 않는 구성, 빠진 필수 절, 모호한 말을 찾는다 |
| **관문** | 단계 할 일이 남았거나, 헌장·관문 메모·레드팀 기록에 빈칸이 있거나, 최종본 점검에 오류가 있으면 프로그램이 승인을 막는다. 승인과 반려에는 대표의 말이, 반려와 취소에는 이유가 필요하다 |

## 누가 무엇을 하나

이 청사진의 원칙은 **"틀리면 안 되는 것은 코드가, 판단은 AI가, 결정은 사람이"**다.

| 코드 (`tf.py`) | AI (수석 비서 + 노련한 파트너) | 사람 (대표) |
|---|---|---|
| 날짜·마감 배분과 재배분, 관문 순서와 통과 조건, 상태판, 출처·계산 파일 대조, 숫자 근거 점검 | 브리핑·기록·세션 인계, 인터뷰, 초안, 추천 하나와 이유, 가설 관리, 사전 부검·레드팀, 공개 자료 수집 | 방향·범위·마감 결정, 관문 승인(채팅에서 한 말을 그대로 기록), 대표만 구할 수 있는 자료 |

AI가 구할 수 없는 자료(로그인·유료·내부 자료)는 "대표에게 요청한 자료"로 등록되어 해결될 때까지 며칠째인지와 함께 브리핑에 뜬다.

## 두 팀 방식

| 단계 | 컨설팅 | 증권사 리서치 |
|---|---|---|
| 0 | 착수 → G0 헌장 승인 | 착수(기준 시점 포함) → G0 헌장 승인 |
| 1 | 진단: SCQA, 이슈트리, 가설 등록, **고스트 덱 초안** → G1 문제 정의 | 기업·산업 이해: 컨센서스, 핵심 변수, 논지 기둥을 가설로 등록 → G1 논지 가설 |
| 2 | 분석: 가설별 워크플랜, 사전 부검, 고스트 덱 채우기 → G2 스토리라인 | 모델·검증: 추정 모델(파일), 시나리오, 공시 원문 대조 → G2 모델 리뷰 |
| 3 | 작성·QA: 결론 먼저, 레드팀 3관점(기록 필수) → G3 최종본 | 리포트·심의: 논지·**컨센서스 대비**·가치평가·촉매·깨지는 조건·고지, 반대 논리 레드팀 → G3 발간 심의 |
| 4 | 버퍼·전달·회고 → G4 | 발간·사후관리: 촉매 일정 등록 필수 → G4 |

리서치 방식은 공개 자료만 쓰고 미공개 중요정보를 받지도 쓰지도 않는다는 규칙을 둔다. 규칙은 [`blueprint/common.md`](blueprint/common.md)(공통), [`blueprint/consulting.md`](blueprint/consulting.md), [`blueprint/research.md`](blueprint/research.md)에 있고, 양식 11개가 [`blueprint/templates/`](blueprint/templates/)에 있다. 각 규칙의 출처와 확인 여부는 [`docs/design_basis.md`](docs/design_basis.md)에 정리했다(ICD 203 분석 기준, CIA 구조화 분석 기법, CFA 윤리기준, FINRA Rule 2241, NEJM 체크리스트 연구 등).

## 실행

Python 3.10 이상, 표준 라이브러리만 쓴다(설치할 것 없음).

```bash
python tf.py new "TF 이름" --mode consulting --deadline 2026-11-13 --path ../my-tf   # 또는 --mode research
cd ../my-tf
python tf.py brief                                        # 수석 비서 브리핑
python tf.py need add "거래처 매출 파일" --owner lead --why "집중도 계산"
python tf.py hyp add "재주문이 늦어진 거래처가 이탈한다"
python tf.py task add "주문 간격 분석" --hyp H1
python tf.py event add 2026-11-09 "중간보고"
python tf.py gate request G1                              # 관문 메모 생성(다시 요청하면 자동 기록만 갱신)
python tf.py gate approve G1 --quote "좋습니다, 진행하죠"
python tf.py replan --deadline 2026-11-20 --why "자료 지연" --quote "20일로 미뤄요"
python tf.py doc redteam                                  # 양식을 work/로 꺼내기
python tf.py check                                        # 품질 점검
python tf.py log "오늘 바뀐 것 / 대표가 정할 것 / 다음 첫 행동"
```

```bash
python -m unittest discover -s tests -v   # 자동 테스트
python bench/run_bench.py                 # 결함 심기 시험 → bench/results.md
python examples/build_examples.py         # 예시 TF 두 개 다시 만들기
```

## 결과 (2026-11-01 측정)

| 시험 | 결과 |
|---|---|
| 자동 테스트 | 33개 통과 (일정 배분·재배분, 숫자 판별, 점검 규칙, 관문 조건, 할 일 취소, 반려 뒤 메모 갱신, 세션 인계, 가설·일정, 양식 꺼내기, 입력 오류 안내, 종료 뒤 브리핑, 명령줄 실행, 결함 심기 회귀) |
| 결함 심기 — 개발 세트 (Claude Code가 만든 문서 8개) | 심어 둔 결함 28개 중 28개 탐지, 잘못 잡음 0 |
| 결함 심기 — 블라인드 v1 (Gemini가 규칙 v1 설명만 보고, 코드를 보지 않은 채 쓴 문서 10개) | **처음 실행: 30개 중 29개 탐지(재현율 96.7%), 잘못 잡음 0**. 놓친 1건은 "비용이 15% 감소할 것 같다"의 15%를 확률 표현으로 착각한 것 → 규칙 수정 후 30/30 |
| 결함 심기 — **블라인드 v2** (Gemini가 규칙 v2 설명만 보고 새로 쓴 문서 10개) | **처음 실행: 36개 중 36개 탐지, 잘못 잡음 0** (새 규칙인 출처 위치 2건, 계산 근거 파일 4건, 컨센서스 절 포함) |

- 블라인드 세트의 정답은 Gemini가 규칙 설명을 읽고 단 것이다. 블라인드 수치는 각 세트의 **처음 실행** 결과다. 수정 뒤 같은 문서를 다시 본 결과는 블라인드 측정이 아니다.
- v1 세트는 규칙 v2에 맞춰 출처 위치를 적고 새 규칙의 정답 21건을 기계적으로 보탠 뒤 회귀 시험으로 쓴다(내역: [`bench/README.md`](bench/README.md)).
- 문서는 모두 가상의 회사·숫자로 된 짧은 합성 문서이고, 규칙이 기계적이라 완벽한 점수가 나오기 쉽다. 이 수치는 "코드가 적힌 규칙대로 동작한다"는 뜻이지, 실제 보고서의 품질을 잰 것이 아니다.

## 한계

- `check`는 표시와 형식을 보는 규칙 점검이다. 논리 비약, 출처가 실제로 그 말을 하는지, 숫자 자체가 맞는지는 잡지 못한다. 그건 AI 파트너와 대표가 원문을 열어 확인해야 한다.
- 표시만 붙이면 점검을 통과한다. 사실에 `[가정]`을 붙여도 통과하고, 표 하나에 출처가 하나만 있어도 표 전체가 통과한다.
- 성공 기준과 본문 위치의 연결은 관문 메모의 체크박스로만 확인한다.
- 최종본이 슬라이드·엑셀이면 점검하지 못한다(`.md`만). 연도만 있는 사실("2011년 설립")과 단위 없는 숫자는 숫자 점검 대상이 아니다. "Python 3.12"처럼 소수가 들어간 이름은 숫자로 볼 수 있다.
- 관문 승인을 AI에게 맡길지는 대표의 정책이다. 지침은 위임을 허용하되 메모를 먼저 채우고 위임한 말을 기록하게 한다. 코드는 그 말이 정말 대표의 말인지 확인할 수 없다.
