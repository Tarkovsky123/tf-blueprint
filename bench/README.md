# 결함 심기 시험

`tf.py check`가 규칙대로 잡는지 재는 시험이다. 문서는 모두 **가상의 회사·숫자·출처**로 만든 짧은 합성 문서이며, 실존 기업과 관계가 없다.

| 세트 | 누가 썼나 | 문서 | 용도 |
|---|---|---|---|
| `dev/` | AI 코딩 에이전트(Claude Code). 점검 코드와 같은 작성자 | 8개 | 회귀 시험(자동 테스트에 포함) |
| `heldout_v1/` | Gemini(Google Antigravity CLI). 규칙 v1 설명만 받고 코드는 보지 않음 | 10개 | v1 블라인드 시험 → 지금은 회귀 시험 |
| `heldout_v2/` | Gemini. 규칙 v2 설명만 받고 코드는 보지 않음 | 10개 | v2 블라인드 시험 |

- 정답 표시: 위반이 있는 줄 끝에 `<!-- expect: 코드 -->`, 필수 절 누락은 첫 줄 `<!-- meta: ... missing=개수 -->`.
- 출처 목록(`sources.csv`)은 세트마다 있다. S1~S6 확인됨, S7 미확인(❓). v2 세트의 S8은 확인됐지만 쪽·표 위치가 없는 출처다. 목록에 없는 번호는 없는 출처다.
- 이 시험에서는 `[계산: 파일]`의 파일이 실제로 있는지는 보지 않는다(TF 폴더가 없으므로). 그 규칙은 자동 테스트가 확인한다.
- `python bench/run_bench.py`를 실행하면 모든 세트를 줄 단위로 대조해 `results.md`를 만든다.

## v1 블라인드 세트 기록 (2026-11-01)

1. 처음 실행: 정답 결함 30개 중 29개 탐지, 잘못 잡음 0.
2. 놓친 1건(`h03_consulting_sourcing.md` 7행): "단기 조달 비용이 15% 감소할 것 같다." 규칙 설명에 확률 표현을 "숫자%"로 적어 두었기 때문에 코드는 15%를 확률 표현으로 보고 모호한 말 경고를 건너뛰었다. 정답을 단 Gemini는 15%를 확률이 아니라 감소 폭으로 읽었고, 그 해석이 규칙의 취지에 맞다.
3. 고침: 확률·가능성이라는 말과 함께 쓴 숫자%만 확률 표현으로 본다. 같은 이유로 "확률 70%" 같은 판단은 출처가 필요한 사실 숫자로 보지 않는다.
4. 고친 뒤: 30개 중 30개. 이 수치는 같은 문서를 다시 본 결과라 블라인드 측정이 아니다.

## 규칙 v2에 맞춘 v1 세트 갱신

규칙 v2에서 점검이 늘어(출처 위치, 계산 근거 파일, 리서치 컨센서스 절) v1 문서에 새 위반이 생겼다. Gemini가 단 기존 정답 30개는 그대로 두고, 아래만 바꿨다.

- `sources.csv`에 S1~S6의 쪽·표 위치를 적었다(v1 문서는 위치 규칙을 모르고 쓰였으므로 출처 쪽을 맞춤).
- 새 규칙이 문자 그대로 적용되는 곳에 정답을 기계적으로 보탰다: 최종본의 파일 없는 `[계산]`·`[추정]` 18곳(CALC_NOFILE), 컨센서스 절이 없는 리서치 최종본 3개(SECTION_MISSING). 사람의 판단이 들어간 정답 변경은 없다.
- 퍼센트·한글 배수·새 모호한 말 규칙은 v1 문서에서 새로 잡은 것이 없었다(잘못 잡음도 없음).
